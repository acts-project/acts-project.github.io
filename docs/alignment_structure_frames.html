Frames for alignable structures

Frames for alignable structures

ActsAlignment::AlignableStructure groups surfaces and defines which rigid-body degrees of freedom may float. To use the composite Jacobians from Composite alignment Jacobians, it also needs an explicit frame: an origin for the rotation pivot and an orientation for its local axes.

Frame conventions

localToGlobalTransform(gctx) returns the structure-to-global rigid transform. Its translation is the pivot in global coordinates; its rotation maps the structure's local axes to global axes. Structure corrections and surface alignment parameters both use local translations and local rotations, each in their own frame. Acts::detail::compositeToComponentJacobian maps structure corrections to the member surface's local parameters, including the rotation lever arm.

Every frame returned by localToGlobalTransform(gctx) maps structure-local coordinates to global coordinates, including for child structures. This return convention does not require applications to store or define geometry in global coordinates. An application can express a child relative to its parent and compose the transforms in the child's callable:

const Acts::Transform3 childToGlobal = parentToGlobal * childToParent;

Both transforms must describe the geometry for the same GeometryContext. The relative transform can also be recovered as parentToGlobal.inverse() * childToGlobal. This allows parent-relative geometry descriptions and reuse of symmetric layouts while retaining a common global representation for the derivative calculations. Alignment corrections still use each structure's own local axes.

addChild() declares membership; it does not perform this composition or move surfaces. Automatic composition through the hierarchy, coordinated updates of member surfaces, and hierarchy constraints are not implemented by this frame API. The user chooses the pivot explicitly; it is not computed from a centroid or inferred from a geometry identifier.

Context-independent and contextual frames

A context-independent frame is copied into the structure at construction:

ActsAlignment::AlignableStructure structure(id, structureToGlobal);

It returns the same frame for every context. This fixes the frame returned by localToGlobalTransform(), not the alignment degrees of freedom, which are controlled by alignmentMask(). The overload is useful for an explicitly chosen pivot and orientation in derivative calculations or tests, and as an initial linearisation frame for the planned structure solver. A fixed global reference frame is one possible use, but is not required.

The stored frame does not follow later changes to the supplied transform or to member surfaces. A solver using it as an initial frame must maintain subsequent frame updates separately. The planned working-state mechanism is described below; the frame API does not yet implement iterative structure alignment.

For a context-dependent frame, supply a callable instead. For example, an application can put its own structure transforms in a geometry-context payload:

struct StructureFrames {
std::unordered_map<Acts::GeometryIdentifier, Acts::Transform3> transforms;
};
ActsAlignment::AlignableStructure structure(
id, [id](const Acts::GeometryContext& gctx) -> Acts::Transform3 {
return gctx.get<StructureFrames>().transforms.at(id);
});

The provider must return a rigid transform consistent with the member surfaces evaluated in the same context. It is called on every query and must be safe for concurrent reads. The structure owns the callable, but captured references and external conditions data remain the application's lifetime responsibility. Returned transforms are values, so callers cannot modify the provider's state through a returned reference.

An iterative solver must apply a correction consistently to the structure frame and to all member surfaces before the next linearisation. The frame provider is a read interface; it does not implement these updates or mutate nominal geometry. Contextual conditions storage remains outside the Alignment library.

For the planned iterative solver, providers seed working frames once per alignment call. The solver will update those working frames together with the member transforms; it must not reset them by rereading a fixed initial provider at each iteration. Final frames must be made available to seed a later alignment call. This working-state and update mechanism is not implemented by the frame API.

Metadata-only structures and Python

The existing constructor AlignableStructure(id) remains available for hierarchy declarations. Such a structure has hasTransform() == false, and querying its frame throws std::logic_error. There is no implicit identity frame. An empty callable is rejected with std::invalid_argument at construction or by setTransform(). A rejected replacement preserves the existing provider.

A frame can also be attached after declaring the hierarchy, or replaced during configuration, using either overload:

ActsAlignment::AlignableStructure structure(id);
structure.setTransform(structureToGlobal);
structure.setTransform(frameProvider);

The transform overload stores a copy; the callable overload owns the provider. Neither overload moves member surfaces. Callers must ensure there are no concurrent readers or writers while replacing a provider. Ordinary IOV changes should use GeometryContext with the installed provider. Replacing the frame alone does not apply a coordinated alignment correction to the member surfaces.

Python exposes the same choices:

from acts.examples.alignment import AlignableStructure
fixed = AlignableStructure(id, transform=structure_to_global)
contextual = AlignableStructure(id, transformProvider=frame_provider)
assert fixed.hasTransform
frame = contextual.localToGlobalTransform(gctx)
late_bound = AlignableStructure(id)
late_bound.setTransform(transform=structure_to_global)
late_bound.setTransform(transformProvider=frame_provider)

Structure derivatives

With a structure frame, ActsAlignment::detail::alignmentToBoundDerivative differentiates the track's bound parameters with respect to translations along and rotations about the structure's local axes. Use a frame consistent with the member surface in the same GeometryContext, including when the frame comes from the current iteration of a fit. This example uses the immediate owner from a validated AlignmentHierarchy:

const auto* owner = hierarchy.structureFor(surface);
if (owner != nullptr) {
const Acts::Transform3 currentFrame = owner->localToGlobalTransform(gctx);
const auto derivative = ActsAlignment::detail::alignmentToBoundDerivative(
gctx, surface, position, direction, pathDerivative,
owner->alignmentMask(), &currentFrame);
// For measurement minus prediction, the residual derivative is
// -H * derivative, where H projects into measurement coordinates.
}

The helper multiplies the unmasked surface derivative by compositeToComponentJacobian(currentFrame, surfaceTransform) and then masks columns in structure coordinates. Masking surface columns before the conversion could discard contributions from those surface axes to an active structure parameter. Without a structure frame, the helper differentiates with respect to local surface translations and rotations and applies the mask in the surface frame.

The native solver currently calls this derivative helper without a structure frame and continues to align individual modules.

Selecting alignables and numbering parameters

detail::makeAlignmentParameterDirectory() assigns positions in the alignment correction vector to selected modules and structures. The caller supplies the standalone module mask; each structure supplies its own mask.

Registering a structure makes it available for selection. Selected structures with enabled parameters must have members and no children, and every member must have a surface placement. A structure with mask None is omitted, leaving its members available for standalone selection. Standalone modules remain selected even with mask None. A placement cannot belong to two selected alignables, regardless of their masks. The registered hierarchy must be acyclic, with each structure and placement registered once. Null entries and duplicate selections are rejected.

The result contains three fields:

  • alignables lists standalone modules first, then active structures, in the supplied order. Each AlignableUnit entry points to the selected object and holds its parameter indices.
  • placementToAlignable maps each member placement to its position in alignables.
  • numParameters counts the enabled parameters.

The factory passes a module or structure pointer and a mask to addAlignable(), which creates an entry and numbers its enabled parameters. It then uses registerPlacement() to associate each module placement with that entry. Registering a placement twice fails without replacing its existing association. Selection validation remains in the factory.

Parameter indices start at zero. Within each alignable, translations Center0..2 precede rotations Rotation0..2; fixed components have no index. For example, if the only selected object is a structure with mask Center0 | Rotation2, every member uses indices 0 and 1. Geometry IDs do not affect numbering. An empty selection or a selection with no enabled parameters is valid.

The directory holds non-owning pointers. Callers must keep all selected structures and placements alive and rebuild the directory after changing selection, membership, or masks. Building it visits the hierarchy and selected members; no track data is involved. Track processing, numerical constraints, solving, and geometry updates remain separate work. The existing solver does not yet use this directory.
